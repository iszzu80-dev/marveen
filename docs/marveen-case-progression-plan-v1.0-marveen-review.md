# Marveen review — Autonomous Case Progression Layer plan v1.0

**Date:** 2026-08-08
**Reviewer:** Marveen (independent, against the live system)
**Reviews:** `docs/marveen-autonomous-case-progression-implementation-plan-v1.0.md`

## Verdict in one line
Excellent architecture and it internalizes almost every hard safety lesson we have — adopt it as the baseline design. But its gap map is wrong on the biggest item (the Case Store already exists and is populated), so it is an EXTENSION of the live COS layer, not a greenfield build; and it is a large program that must be phased thin-first with the eval suite built early.

## What is strong (endorse as-is)
- **Outcome, not action** (`email_sent` ≠ done; `COMPLETED` only on Definition-of-Done + evidence). This is exactly our verification discipline. The Semantic Completion Verifier is the anti-premature-completion guard.
- **Single controlled write chokepoint** — no write-capable MCP/API tool reachable on a bypass path; all side effects through the Action Executor. This is gate-at-the-choke-point, done right, plus idempotency-key + readback + OUTCOME_UNKNOWN→readback (no blind retry).
- **Hard gates never automatic** (payment, investment, contract, legal, bank, ownership, phone). Correct and non-negotiable.
- **Domain isolation as CODE** (mandatory DomainContext, cross-domain denied by default, connector/memory/policy per domain). This is our connector-identity-as-scope-boundary principle made architectural — the same rule that keeps personal_cases and zst_cases from ever mixing.
- **Delegation Envelope** (intent/recipient/data/financial/expiry/revoke + policy_hash) instead of a global level-3 email-send. Bounded delegation is the right answer to "do routine things yourself."
- **Prompt-injection = untrusted data** (email/doc/web cannot modify goal/policy/envelope/gate/recipient). Matches our untrusted-input discipline.
- **Shadow-first → canary with 0-incident gates**, reuse of scheduler/approval/autonomy/memory, no LangGraph/Temporal/n8n. Disciplined, dependency-light, matches how we ship.

## What I push back on (fix before the WP0 change set)
1. **The gap map is WRONG on the Case Store — it is NOT missing, it EXISTS and is live.** The plan lists Case Store, `case_id` model, and event ledger as MISSING. Reality (verified against the running DB + repo): `src/cos/case-store.ts` + `case-engine-core.ts` exist; `personal_cases` = 48 rows, `zst_cases` = 27 rows, `personal_case_events` = 182 rows; plus `email-ingest`, `dispatch-gate`, `cos-documents`, campaigns, connector-health. The email→case intake ALREADY WORKS (that is how the 27 ZST cases exist), and the Mission Control UI already reads them. So this is a CONSOLIDATION/EXTENSION of the live COS layer into a formal domain-scoped progression kernel — not greenfield. Consequence: (a) the foundation effort is smaller than the plan implies; (b) the real risk shifts to MIGRATION — WP1 must extend the existing `personal_cases`/`zst_cases` into the unified domain-scoped `cases` model WITHOUT breaking the live intake, the existing cases, or the Mission Control views. Reframe WP0/WP1 accordingly.
2. **Scope is a program, not a sprint (12 WPs, 7 phases, ~13 stores).** The phasing spine (Case Foundation → Shadow → Internal Autonomy → Action Executor → Canary) is right. Compress the first deliverable: add the Outcome Contract + progression fields + shadow resolver ONTO the existing case-store as a thin, shippable slice; prove the model + isolation + a couple of real shadow runs before building the full kernel/action-executor. Value early, validate, then layer.
3. **The load-bearing risk is LLM-reasoning-in-the-loop + `safeToInfer`.** Deterministic policy/lock/gate is fine; but per-case-per-wake goal-interpretation, planning, next-best-action, and "safe inference" are LLM work whose non-determinism, feeding actions, is the core danger. The mitigations (deterministic policy gate, hard chokepoint, shadow-first, narrow envelopes, no-progress threshold, preCheck-skip) are good — but the eval/replay suite (§33) is what actually proves it is safe. Build it EARLY and gate every phase on it, not just at WP12. Keep the first envelopes NARROW (existing-thread, factual-only, financial 0).
4. **Baseline SHA is wrong for us.** The plan baselines on `develop @ 8323058` (that is bare upstream origin/develop). Our LIVE develop is now `c8312b3` (v1.31.0, post-update, and it already contains the whole COS layer + today's work). WP0's audit must run against OUR real develop, not upstream — otherwise the "exact file-by-file WP0 change set" maps against the wrong tree and will re-flag existing code as missing (which is exactly what the gap map already did).
5. **Repo target framing.** The header says `Szotasz/marveen`; the CoS layer is fork-local product logic (it is not in upstream and should not block on it). Build on our fork/develop, same as the existing COS layer.

## Recommendation
Adopt the architecture + safety model as the baseline — it is the right design and I fully endorse the outcome-driven, chokepoint-gated, domain-isolated, shadow-first shape. Before the WP0 change set: (1) redo the gap map against the LIVE COS layer (Case Store etc. = PARTIAL/EXISTS, not MISSING); (2) reframe WP1 as extend-and-migrate the existing `personal_cases`/`zst_cases`, preserving the live intake + Mission Control; (3) baseline on our develop `c8312b3`; (4) pull the eval/replay suite forward to gate each phase; (5) ship a thin Case-Foundation+shadow-resolver slice first for value + validation. The plan is genuinely good; it needs a grounding pass against what already runs.
